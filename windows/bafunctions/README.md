# RoofSpan BAFunctions — Burn-side PostgreSQL bootstrap credential generator

**HUMAN REQUIRED (Windows build).** This native DLL is a *BAFunctions* hook for the WiX v4
`WixStandardBootstrapperApplication` (WixStdBA). It is the smallest officially-supported WiX v4
mechanism to run code inside Burn *before the chain executes* while keeping the stock installer UI.

## Why it exists
`WixStandardBootstrapperApplication` has **no secure random-number generator** for Burn variables. For a
**fresh RoofSpan-managed PostgreSQL install** the superuser/bootstrap password must exist **before** the
EDB PostgreSQL package runs (EDB establishes the `postgres` password at install via `--superpassword`).
Generating it afterward in the MSI would be a circular, unauthenticatable path.

`OnDetectComplete` (after Detect, before Plan):
- If `PgSuperPassword` is already non-empty → **do nothing** (enterprise/external override supplied).
- Else if `RoofSpanPgPresent == 1` → **do nothing** (RoofSpan-managed PG already installed; upgrade).
- Else (fresh managed install) → generate **32 CSPRNG bytes → 64 hex chars** and `SetVariableString`.

`PgSuperPassword` is declared `Hidden="yes"` in `bundle.wxs`, so Burn **redacts** it in logs, including on
the EDB `--superpassword` command line and when handed to the MSI `PG_SUPERPASSWORD`. It is **not
persisted** by Burn. The RoofSpan **application** DB password is a *separate* random value generated by
`winbuild/bootstrap_db.py` and is the only password written to the deployed `DATABASE_URL`.

## Build (Windows + MSVC + NuGet)
1. Add a reference to NuGet `WixToolset.WixStandardBootstrapperApplicationFunctionApi` (pin the version to
   match your `wix` toolset). It provides `BalBaseBAFunctions.h`, `IBAFunctions.h`, and the
   `BA_FUNCTIONS_*` structs.
2. Compile `RoofSpanBaFunctions.cpp` as a DLL (x64), exporting `BAFunctionsCreate` via
   `RoofSpanBaFunctions.def`. Link `bcrypt.lib` and the WiX `dutil`/`balutil` static libs from the NuGet.
3. Produce `RoofSpanBaFunctions.dll`.

> The `.cpp` follows the documented v4 BAFunctions pattern; **reconcile the exact method signatures**
> (`OnDetectComplete`, `GetVariableString`/`BalGetStringVariable`, `GetVariableNumeric`,
> `SetVariableString`, `BAFunctionsCreate`, `BalBaseBAFunctionsProc`) against the pinned NuGet headers —
> the WiX BA API surface changes between minor versions.

## Wire into the bundle
`installer/build.ps1` requires `-BaFunctionsDll <path\RoofSpanBaFunctions.dll>` and passes it to
`wix build` as `-d BaFunctionsDll=...`. `bundle.wxs` references it:

```xml
<Payload Id="RoofSpanBaFunctions" SourceFile="$(var.BaFunctionsDll)" bal:IsBAFunctions="yes" />
```

## Validate on a real box (HUMAN REQUIRED)
- Fresh install with **no** unrelated PostgreSQL: EDB installs `RoofSpanPostgreSQL` on port **5442** with
  the generated superpassword; MSI `RoofSpanBootstrap.exe` provisions the `roofspan` role/db and writes
  the deployed `DATABASE_URL`. Confirm `PgSuperPassword` appears **redacted** (`*****`) in the Burn log.
- Fresh install with an **unrelated** PostgreSQL on 5432 present: RoofSpan still installs its own instance
  on 5442 (unrelated PG is not adopted, `RoofSpanPgPresent` is false).
- Upgrade of an existing RoofSpan install: EDB is skipped (`RoofSpanPgPresent`), no new password is
  generated, and the deployed config is preserved.
- Enterprise override (`-DPgSuperPassword=...` at install): the supplied credential is used and the hook
  generates nothing.
